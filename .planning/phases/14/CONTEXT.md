## Durable decisions

- D-135. (adoption of ticked phases the documents cannot derive complete; owner 2026-09-11): the import writes one declared completion record per roadmap-ticked phase whose legacy table (SUMMARY.md plus every UAT item pass or skipped with a reason) does not derive Complete, provenance declared-at-import, stored at adoption.declared_completions[] (ADOPT-1, 332cdc2b; not under verification, which the store reserves for verification transactions), never for an unticked phase, never where the legacy table derives Complete, never where a native completion exists, and never by a caller. The record claims nothing (claims: [] is written), edits no document, and yields the moment a native context is approved for that phase. Binds every adoption of a 3.x tree, this project's phases 9, 10, 11, 12, 13, 27, 28 and 29 included. If wrong: adoption either lies about history or walls every 3.x adopter out of execute-next.
- D-137. (automatic at first touch or an explicit operation; draft K2): both, from one function. The import writes the record at a fresh first touch; an owner-run cadence_apply adoption-declare {phase, request_id} writes the same record with provenance declared-at-adoption for a store imported before the record existed or a row ticked after import, refusing a derivable phase (declaration-unneeded naming the derived status), an unticked phase (declaration-unticked naming the roadmap line) and a natively completed phase (declaration-native naming the completion id); the record's content is always computed by the binary from the documents. Progress shows the provenance word. If wrong: an early adopter or a post-import tick has no binary path out of a permanent conflict.
- D-138. (cad-health and cad-report as alias names; draft K3): no aliases. /cad-progress renders status, issues, record, captures and next in one answer; --stats and --trace die with the reads log. D-133 kept review aliases because three commands select three distinct targets; health and report select nothing progress does not already show. If wrong: two more compiled skills rendering sub-views of one query.
- D-140. (what the log records for a refusal; draft K5): the typed refusal envelope verbatim, bounded with a cut marker, plus a typed located object and at; stable_reason (execution_service.rs:2295-2304) stops discarding detail for every code outside its five. A summary alone repeats today's gap; the envelope alone cannot be joined without parsing prose. If wrong: cad-suggest and cad-why read reasons they cannot join to a line.
- D-141. (the missing-return answer; draft K6): the front door records the host launch through one apply operation (dispatch-launched {dispatch or attempt, agent_id}) as it spawns the worker; cadence stop is the one SubagentStop registration and writes an Interrupted observation for any dispatch kind whose launch id matches (execution dispatch, verification attempt, review attempt), silent and exit 0; a patch arriving after Interrupted is still accepted; Interrupted without a patch is the detected failure, rendered by progress as dispatch <id> interrupted, no return, and execute-next re-serves that dispatch only after an explicit continuation record (D-113, never a blind redispatch); no wall-clock timeout and no lease expiry, age is shown as store generations since launch. Known gap, written down: a host that never fires SubagentStop leaves the dispatch launched, no stop, no return, and the owner's resume decides. If wrong: a dead worker is indistinguishable from a slow one and the same candidate is re-served forever.
- D-142. (phase 9's seven UAT items; draft K7): never flipped, by anyone. The record does not edit UAT.md; derivation for phase 9 comes from the declared record, progress shows 150 pass, 7 fail beside declared at import, unverified, the guard refuses a host edit of phases/9/UAT.md (guard/mod.rs:299-309), verify-plan7.json stays unretained history. Generalized: adoption never edits a document. If wrong: a document is rewritten to fit a rule, which is the D-114 violation.
- D-143. (a time on decision records; draft K8): every decision record written from now on carries at, seconds since epoch from the clock the runners use, optional in the schema and absent on imported rows (store/model.rs:100-107 carries none today). Store generation answers in what order, never when. If wrong: a live failure cannot be placed in time.
- D-144. (the phase of a capture; draft K9): the phase is a typed field on the ItemRecord, refused when it names an undeclared phase, never carried inside the text as 3.x did; recall filters by it. If wrong: captures cannot be listed by phase without parsing prose.

## Truths

- T1. When a tree whose roadmap ticks a phase the documents cannot derive complete is first touched, the owner sees that phase reported complete as declared at import with every document byte unchanged.
- T2. When the owner asks for progress, the owner sees every phase's derived status, the located issues and the one next action.
- T3. When the owner asks why a file line is as it is, the owner gets the chain text byte-identical to the fixed expected text for that repository.
- T4. When the owner asks for retune suggestions, the owner gets each suggestion with its config key, the value in force, the proposed value and the decisions it counted, with no config key changed.
- T5. When the owner submits a capture, the owner sees it as a captured item with its kind and phase, with the queue's bound reported when exceeded.
- T6. When an operation is refused, the owner sees the refusal in the log with its code, its located detail and when it happened.
- T7. When a dispatched worker stops without returning a patch, the owner sees that dispatch reported as interrupted with no silent redispatch offered.
