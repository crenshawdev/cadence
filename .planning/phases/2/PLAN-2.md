# Phase 2: The golden harness - Plan 2 (the recorder over the whole surface)

## Goal

This plan must not be dispatched until plan 1 has landed (it extends the
recorder, manifest and bundles plan 1 commits), and plan 3 must not be
dispatched until this plan's recordings and `normalization.json` are committed.

Parity against `v3.7.12` is a test that runs, not a claim. This plan finishes
the JavaScript half of the instrument: the recorder plan 1 proved on the
slice's read operations learns to build a throwaway git repository for the
operations that need one and to capture the bytes a write operation leaves
behind, every remaining source of nondeterminism is pinned or covered by a
named rule that is committed as DATA the Rust side reads too, the full
manifest is recorded, and a drift check fails when a recording no longer
matches what the frozen code produces. Plan 3 (sequential, after this one) is
the Rust side that reads these recordings. Nothing in the binary is ported
here, and nothing under `cadence-core/` changes.

  byte-identical files under `recordings/`, including the invocations that run

### Task 3: The clock rules are committed data and every rule is justified by its site

- **Files:** crates/cadence/tests/golden/record.mjs, crates/cadence/tests/golden/normalization.json, crates/cadence/tests/golden/recordings/
- **Action:** Cover each source the ROADMAP names. Locale and sort order: the
  `TZ`, `LC_ALL`, `LANG` pins from plan 1 Task 2. Git SHAs: Task 1.
  Interpreter: the `node` key plan 1 Task 2 records (Task 4 acts on it).
  Correlation ids: `corr` derives from the caller's `--sha` (D-14), a manifest
  input, so no rule. Absolute paths: the `<FIXTURE>`/`<REPO>` substitution from
  plan 1 Task 2 - and read-side failure outputs carry them too (ROADMAP), so the
  substitution runs over stderr and refusal `detail` strings as well as `ok`
  envelopes. That substitution is the OTHER half of the cross-side contract, and
  plan 3 must reproduce it or no answer from a live scratch directory can ever
  match: the pipeline is, IN THIS ORDER, substitute `<FIXTURE>` for the scratch
  root and `<REPO>` for the repository root, THEN apply the rules below. Plan 3
  Task 5 applies the same two substitutions to the answer's `stdout`, `files`
  and `deleted` before its rule pass; state the order in both places and never
  reverse it. The clock: the
  mechanism is DECIDED here - a NAMED rule per field, carried as data in
  `crates/cadence/tests/golden/normalization.json`, which the recorder LOADS
  at start (refusing to run if it is missing, malformed, or holds a `pattern`
  `new RegExp` rejects) and applies to `stdout` and `files` before writing each
  recording, and which plan 3's Rust test loads and applies to the binary's
  answer with the same semantics, so both sides meet on the token (D-05: the
  Rust side can never ask `node` what was normalized, so the rules must be a
  file it reads). The file is `{"mechanism":"named-fields","rules":[...]}`;
  each rule carries `id`, `target` (`file` or `stdout`), `path_suffix` (for
  `file`: matched against the END of the fixture-relative path, so one rule
  covers `UAT.md` in every phase) or `key` (for `stdout`: a dotted path into
  the parsed envelope), `pattern` (a regular expression written ONLY in the
  dialect subset JavaScript's `RegExp` and Rust's `regex` crate share -
  literals, `\.`, `[...]`, `^`, `$`, and the quantifiers `+`, `*`, `?`, `{n}`
  and `{n,m}`, which both engines read identically. `\d` is BANNED and `[0-9]`
  is written instead: JavaScript reads `\d` as ASCII-only while Rust's `regex`
  reads it as Unicode `Nd`, so a `\d` rule would normalize a non-ASCII digit
  run on the Rust side that the recorder left alone - the one dialect
  difference that bites here, and the reason this list is enumerated rather
  than described; no lookaround and no
  backreferences. The pattern STRING carries no flags and each side supplies
  globality ITSELF: the recorder compiles `new RegExp(pattern, 'g')`, because a
  non-global `RegExp` replaces only the FIRST match while Rust's `replace_all`
  is global, and a rule that normalizes one match on one side and every match on
  the other is a silent asymmetry no Verify in this phase would catch),
  `replace` (literal text, no group references, and never containing `$` -
  Rust's `replace_all` EXPANDS `$name` in a replacement while JavaScript's does
  not, so the loader on both sides refuses a `$` outright and the Rust side
  passes the replacement through `regex::NoExpand`,
  carrying the token `<NOW>` for an ISO-8601 instant or `<TODAY>` for a day
  stamp, with the key or prefix repeated so the pattern can match the whole
  field, e.g. a `"ts":"..."` pair becomes `"ts":"<NOW>"` and an `Updated: ...`
  line becomes `Updated: <TODAY>`) and `site` (the frozen source line that
  writes the value, so a reader knows why the rule exists). Semantics,
  identical on both sides: a `stdout` rule replaces every match of `pattern`
  in the string at `key` and is a no-op when the key is absent or not a string;
  a `file` rule applies to every `files` entry whose path ends with
  `path_suffix`, splitting the text on `\n`, SKIPPING every line that appears
  verbatim ANYWHERE in the pre-run copy of the TREE (Task 2's map, unioned
  across every path, never the same path alone), replacing every
  match in the remaining lines, and rejoining with `\n` - so a seeded `ts` line
  and an untouched `started:` line keep their real values, and a binary that
  re-stamps a line it should have left alone is caught rather than normalized
  away (D-12). The skip test is TREE-WIDE and not path-local, and the difference
  is load-bearing for `renumber` and `milestone-prune`: those MOVE a file to a
  path that had no pre-run copy, so a path-local test would read the moved
  `UAT.md`'s `started`/`updated` lines as newly written and normalize them - and
  a Rust implementation that wrongly RE-STAMPED them would produce the same
  tokens and pass. Unioned across the tree those lines are recognised as copied,
  keep their real values, and a re-stamp fails the comparison. The union only
  ever skips MORE lines, so it can never hide a divergence a path-local test
  would have caught. The rules to write, one per clock site a recorded invocation
  reaches: trace record `ts` in `.planning/trace.jsonl` (`lib/trace.mjs:415`);
  reads record `ts` in `.planning/reads.jsonl` (`lib/read-trace.mjs:392`); the
  cursor's `updated` both in the `cursor set` envelope (`stdout` key
  `cursor.updated`) and as the `Updated:` line of `.planning/STATE.md`
  (`planning/cursor-set.mjs:147`); UAT frontmatter `started` and `updated` in
  `UAT.md` (`planning/uat.mjs:40,121` - read `renderUat` for the exact line
  shape before writing the pattern); the capture note bullet's leading day
  stamp in `.planning/CAPTURE.md` (`lib/capture-file.mjs:116`); and
  `duration_ms` in the `.planning/trace.jsonl` event `traceProvider` appends
  (`review-provider.mjs:622`, `Date.now() - meta.started`), which varies per run
  WITHOUT being date-shaped - the enumeration in the next task's Verify sweeps
  for date shapes and cannot see an integer, which is exactly why this one needs
  a named rule. `traceProvider` is reached from `review-provider.mjs:164` on the
  refusal path, after `beginProviderCall` at 1371/1411/1450; if the executor
  finds that every recorded `review-provider` arm returns BEFORE
  `beginProviderCall`, record THAT as the reason no rule is needed rather than
  deleting this sentence. The rotation
  markers (`lib/trace.mjs:486`, `lib/read-trace.mjs:580`) and `mirrorFiled`'s
  date (`issue-filing.mjs:507`) are reached by no recorded invocation - the
  seeded traces sit under the rotation cap and the issue-filing entries are
  offline refusals that return before filing - so they get NO rule (D-12: a
  rule nothing needs hides a divergence); if the enumeration in the Verify
  shows one reached, add its rule with its site. `release-bump` takes `--date`
  and the manifest pins it: no rule. Never a blanket ISO-8601 or `YYYY-MM-DD`
  scrub: fixture inputs carry dates (`Gathered: 2026-08-26`, seeded `ts`
  values) that a binary could echo wrongly. REJECTED mechanism, recorded so no
  one re-litigates it: a frozen-`Date` shim through `NODE_OPTIONS=--import`
  would leave a literal instant in the recording that a reader cannot tell

  named here as `--no-normalize` (skip rule application); the executor may
  rename it, keeping the Verify's meaning, and it exists only for the negative

- **Sequential between plans 1 and 3.** This plan shares `record.mjs`,
  `operations.json` and `recordings/` with plan 1 - the phase needed more
  capacity than one plan's eight-task ceiling, and the contract's answer to
  that is more plans, sequential where they share declared files. Plan 3 shares
  no file with this plan but reads what it commits. Both dependencies are
  stated in the Goals where the dispatcher reads before deciding;
  `execute.md:28` runs plan files in numeric order and
  `parallelization.enabled` is false (measured 2026-09-05) - confirm it still
  is before dispatching the phase.
- **The clock mechanism is named-per-field rules, decided here, not left to
  the executor.** The two candidate mechanisms produce different recording
  bytes, plan 3 is written against the rules' output, and the Rust side can
  only apply rules it can read. The frozen-`Date` shim is rejected in Task 3
  with its reasons; it is not a fallback, because a fallback would be a second
  contract plan 3 would also have to understand.
- **AC6 says "the two normalized fields".** It was written before the
  revision. The normalized fields are every rule in `normalization.json` -
  trace and reads `ts`, the cursor's `updated` in the envelope and in
  `STATE.md`, UAT `started` and `updated`, the capture note's day stamp - and
  Task 4's Verify enumerates every date-shaped value across the recordings and
  requires each to be a fixture input, a manifest input or a recorder
  constant, which is the property AC6 was reaching for.
- **AC2 says "~13 operations".** It was written before the revision; the
  Verify applies it to every recording.
- **The interpreter is a pinned source of nondeterminism, not a proven one.**
  A cross-major run producing identical recordings cannot be shown on this
  machine (Node 26.8.1 is the only interpreter and no version manager or
  container runtime exists), and with the major recorded in every file two
  majors could not produce identical recordings by design. The pin replaces the
  proof: the recordings name their major, `--check` refuses another before
  comparing, and CI runs on the named one. Node's own stderr diagnostics are
  the known variance; the frozen scripts' logic is not expected to differ, and
  a later re-record under a new major is a named event, never a mystery diff.
- **`--check` refines D-07's "dirty working tree" wording.** D-07's mechanism
  (re-run, fail on difference) is kept; comparing against scratch instead of
  overwriting is what lets AC3's hand edit be reported rather than repaired.
- **Fixture provenance is checked locally only.** Rebuilding from the tag
  needs `v3.7.12` in the checkout, and the CI jobs clone at depth 1 without
  tags; the drift job checks recordings against the frozen JavaScript, which is
  the property that matters in CI.
- **`CADENCE_TEST_SEAM` stays closed (D-13).** `detect-commands`'s
  reachability is pinned by the scratch PATH (node and git only) rather than
  by `CADENCE_DETECT_REACHABLE`, so the recording is the unreachable arm with
  the tool named in `warnings[]`.
