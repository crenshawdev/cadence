## Durable decisions

- D-201. The debug session is a binary-owned record: symptom, hypotheses each with a state (untested, testing, refuted, confirmed) and a rank reason, observations each with the test run, its result and what it rules in or out, the attempt count, status (open, resolved) and resolution. The record is rendered to .planning/debug/<slug>.md, which the guard protects like phases/<N>/SUMMARY.md; nothing but the binary writes it. list, status and continue are reads of the record, and a continued session is fed from the record alone: no host file, no grep, nothing re-asked.
- D-202. A debug fix is reviewed as a staged tree under a root-debug scope with no phase. The rail's scope carries a root-debug variant beside the phase scope; the material identity is Staged{base_id, index_id}; an empty index is refused as nothing staged, never read as a completed empty check. A match or an inconclusive check admits one fire with caller debug on the staged tree, home reviews/<fire>. A blocking fire settles only through the receipts rail: a gate-pass receipt, a reasoned override receipt, or one narrowed re-arm round that validate_rearm caps; raw findings grant nothing, and no settlement-verification layer is added.
- D-203. Recall is a query operation on the wire: recall {query, limit?, phase?}, answering hits with source and phase, filtered to the phase when one is named. debug-open reads recall for the symptom under the effective memory.backend: hits on the record under builtin, none and no corpus read under none. The recall corpus is unchanged by this phase and does not read the debug or spike records.
- D-204. The spike is a binary-owned record whose question, decision and risk-ordered criteria are recorded before any experiment material exists; the record is rendered to .planning/spikes/<slug>/SPIKE.md, which the guard protects, and no other file is written inside that directory. The verdict is one of validated, invalidated, inconclusive with an observed result per criterion; after the verdict the criteria cannot change. The throwaway material's location is recorded at close and is never a permanent write. The ten spike directories that exist at HEAD are history and are not migrated.
- D-205. The command reference is a table compiled inside crates (name, cluster, description) that is the one source for the rendered SKILL.md description front matter and for the help answer. Help lists every user-invocable skill the binary installs, one by name with the cad- and slash prefixes optional, and the closest names on no match. COMMANDS.md is deleted as replaced, and cad-help is rendered by the binary like the other skills.
- D-206. Consult is a consult arm of the provider port: the situation goes out fenced and capped, the angles come back typed, and both are recorded on the debug record. The offer appears once per dead-end on observable state only, the attempt count at review.consult.attempt_threshold or every hypothesis refuted, and only when review.consult.enabled is true and a provider model exists at review.consult.tier; it is never automatic and a claude-subagent consult does not exist.

## Truths

- T1. When a debug session is continued after any recorded observation, the owner sees the same symptom, hypotheses with their state, observations and attempt count, read from the binary's debug record and nothing else.
- T2. When a debug session is opened, the owner gets recall for the symptom under the effective memory.backend: hits with source and phase on the record under builtin, none and no corpus read under none, and the recall query filtering by phase.
- T3. When resolve is requested on a debug session with a staged fix, the owner sees the index risk-checked under a root-debug scope with no phase, an empty index refused, and a match or an inconclusive check firing the shared risk-surface reviewer on the staged tree.
- T4. When a blocking debug fire returns findings, the owner sees resolve refused until a gate-pass or a reasoned override receipt names that fire, with at most one narrowed re-arm round.
- T5. When a debug session records a dead-end (the attempt count at review.consult.attempt_threshold, every hypothesis refuted), the owner sees the consult offered once for that dead-end, only when review.consult.enabled is true and a provider model exists at the tier, and the angles recorded on the record when accepted.
- T6. When a spike is opened, the owner sees its question, decision and risk-ordered criteria recorded before any experiment material exists; a verdict outside validated, invalidated, inconclusive refused; and the criteria unchangeable after the verdict.
- T7. When help is asked, the owner sees every user-invocable skill the binary installs, by cluster, with its compiled description; a name answering that one skill; no match listing the closest names; a skill absent at HEAD never listed.

## Flagged assumptions

- The debug and spike records are store records rendered to markdown by the binary's own renderer, the way phases/<N>/SUMMARY.md is, and protected_target covers the rendered paths.
- The reviewer dispatch is the host's (a subagent the skill's model launches under the cad-review-delivery contract); checks drive the binary's admission, return and consequence records and never a model.
- The consult provider is reached through the existing transport trait; checks inject a scripted transport the way phase10_provider_tests.rs does, and no network is touched.
- A fixture git repository built by the test with fixed dates stands in for the project in every staged-fix check; the risk surfaces are answered in the fixture's config layer.
- The recall corpus and scoring are as the recall module has them today; T2 adds the wire operation and the phase filter, not new corpus tiers.
- The frozen JavaScript and prose for each replaced surface are deleted from this branch by the plan that replaces it (rule of 2026-09-11); their tests go with them.
