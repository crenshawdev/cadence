### Prompt 2, the owner's specification, verbatim (2026-09-22, with the owner's corrections of the same day)

> ## Shaping how Cadence derives tests from plans
>
> Change Cadence's plan-to-test behavior so it produces bounded, meaningful evidence for the user's approved requirements. This is product behavior for projects Cadence manages, distinct from instructions for testing the Cadence rebuild itself. While making this change, obey Cadence's own development rules, including no Python in its code, suite, runner grammar, or contracts.
>
> First inspect the existing planning, test-contract, generation, review, and evidence paths. Identify what already satisfies this policy and make the smallest coherent change. Reuse existing records and mechanisms. Do not assume new schemas, runner adapters, a policy language, or a static-analysis subsystem are needed.
>
> **How far test generation goes**
>
> - Derive testing obligations from approved behavior and the changes required to deliver it. A plan step is an organizational container, not a unit-test target. Decompose it into independently testable responsibilities.
> - For each responsibility, identify meaningful input classes, decision boundaries, and failure responses supported by the requirement. Do not invent behavior to obtain an expected answer. Flag ambiguous requirements for clarification.
> - Stop adding cases when they distinguish no additional required behavior or meaningful failure. Do not optimize for test counts, a test per function, blanket permutations, or arbitrary coverage percentages. Reuse existing adequate evidence and relevant regression tests.
> - Default generated unit tests to one responsibility, one behavior, and at most one simulated external seam. Test real owned logic with supplied observations and independently justified expectations. No full-step workflows or child processes in this unit-test policy. A generated test may depend only on the target project's language toolchain and test libraries from that language's own package ecosystem, including its mocking libraries; never on another language's runtime, a program installed on the host, specific hardware, or the state of the machine. It gives the same result on any machine where the project builds. A fresh temporary directory the test creates for itself is allowed and counts as its filesystem seam: the test reads and writes only inside it, starts no program in it, and asserts nothing that depends on a particular filesystem's permissions, case sensitivity, symlink support, or crash durability.
> - Pure gathering adapters receive no unit tests under this policy. Separate any owned parsing, validation, error interpretation, or decision logic before classifying an adapter as pure gathering.
> - Fakes must not supply the decision being tested. Judge this relative to the responsibility under examination, not by banning all domain-valued fake outputs. Do not prescribe mocks when plain values suffice.
>
> **Evidence and completion**
>
> - Using existing structures where possible, link each testing obligation to its requirement, production responsibility, inputs or seam, expected observable behavior, and existing or proposed test. State the meaningful defect the assertion should catch.
> - Keep planned, written, reviewed, executed, and passed evidence distinguishable. A test name, declaration, comment, or model assertion is not execution evidence. A passing result is not by itself evidence that the assertion tests the right behavior.
> - If a requirement concerns integration, GUI interaction, real persistence, performance, or an assembled workflow, do not claim constituent unit tests prove it. Record the remaining verification obligation explicitly. Unit-test success alone must not close that obligation.
> - Broader verification belongs to a separate, explicitly approved project verification scope. Do not automatically generate it, silently waive it, relabel it as a unit test, or weaken the requirement. Report what remains unverified and whether it blocks completion under the approved plan.
>
> **Project policy and enforcement**
>
> - Keep the methodology language-neutral. Generate tests in the target project's approved language and framework. Cadence's Rust implementation is not a requirement that every managed project use Rust.
> - Do not use language neutrality as permission to introduce Python into Cadence's own implementation, suite, grammar, or contracts, or to add unsupported runner integrations. Preserve current runner boundaries; raise any necessary change separately.
> - Distinguish Cadence launching an approved test runner from a test launching another program. The runner is the execution mechanism; test code remains subject to its dependency policy.
> - The binary should enforce facts it can actually establish: required links, valid records, permitted execution configuration, evidence presence, and legal completion transitions. Review must assess requirement fidelity, assertion adequacy, and whether a fake bypasses the tested decision. Connect required review outcomes to existing completion gates.
> - Do not claim that names, type labels, self-declarations, source-pattern checks, or a passing runner prove semantic correctness or absence of every indirect dependency. Report unsupported or inconclusive checks honestly. Do not turn incomplete analysis into a claim of compliance.
>
> Before editing, summarize the existing behavior, necessary changes, and unresolved policy choices. Afterwards, report what changed, what is mechanically enforced versus reviewed, what was actually executed, and the remaining limitations. Do not broaden the task into unrelated test infrastructure.

## Durable decisions

- D-225. A truth names the decision the project owns. The part only a running program shows is listed apart, under a Live verification heading in the context's scope, and becomes an observation in the map of the phase that first makes it runnable (docs/architecture/acceptance.md:166-171). Passing unit tests do not close it. No field is added to a truth; the context instructions say this where the context author reads them.
- D-226. The plan instructions carry Prompt 2's derivation rules in their own words: tests are derived from approved behavior and the changes that deliver it; a plan step is a container, not a test target; each test covers one responsibility and one behavior with at most one simulated seam; expected values come from the requirement and are never invented to get an answer, and an ambiguous requirement is flagged; each case names the defect it catches; cases stop when one catches nothing new, with no test counts, test per function, permutations or coverage targets; adequate existing tests are reused; a pure gathering adapter gets no unit test once its owned parsing, validation, error interpretation and decisions are separated out; a fake never supplies the decision under test, judged against the responsibility; plain values are used where they suffice; tests are written in the project's own approved language and framework. A test depends only on the project's language toolchain and test libraries from that language's own package ecosystem, never on another language's runtime, a program installed on the host, specific hardware or the state of the machine, gives the same result on any machine where the project builds, starts no program, and may use a fresh temporary directory it creates as its filesystem seam, reading and writing only inside it, starting no program in it and asserting nothing that depends on a filesystem's permissions, case sensitivity, symlink support or crash durability. Cadence launching the approved runner is not a test launching a program.
- D-227. One check per truth stays (acceptance.md:147-151; plan/limits.rs:155-192). A check's test file is the task's tests-only file, holding one test per responsibility; the check names the test that causes the truth's trigger, and the task action names the others, each with the defect it catches. Every test of the task is committed before the red run. The binary's close rule is stated in the plan instructions and the executor contract: the test file's bytes must be identical at the red commit, the green commit and the task's completion commit, with the same command at red and green, or the task cannot close (execution/receipts.rs:475-482).
- D-228. Plan review stays advisory. The plan-review intent and the reviewer brief's plan line gain three questions: does each test serve its requirement, is each assertion adequate to catch the defect it names, and does any fake supply the decision under test. The required review outcomes remain the two that already gate completion: the owner's inspection of each check at execution-plan-complete and the verifier's verdicts at verification-complete. No gate is added before plan-submit.
- D-229. The verifier contract states what is not evidence: a test name, declaration, comment or model assertion is not execution evidence; a passing run alone does not show that the assertion tests the right behavior; a check that is unsupported or inconclusive is reported as such and never turned into a claim of compliance. Names, type labels, declared boundaries, source patterns and a passing runner are not claimed to prove semantic correctness or the absence of an indirect dependency.
- D-230. Language and runner boundaries stay as they are. The executor contract's manifest table keeps its four rows, Python included, because it describes a managed project's tests and starts nothing. The runner's result grammar is unchanged. That independent verification accepts only a cargo or nextest summary (verification/runner.rs:46-64), so a managed project in another language cannot complete verification, is raised as a milestone 13 issue, proposed to the owner before filing. Cadence's own code, suite, runner grammar and contracts gain no Python.
- D-231. plan-submit refuses a check whose test file is blank after trimming, with a typed refusal naming the check's slot, in the same content check that refuses a blank command or expected value (plan/limits.rs:8-45, 110-123). A check with no test file can never launch (execution/runner.rs:367), so the refusal moves to before the owner's approval. Boundary, fakes and the other carried fields stay unparsed, as the owner decided on 2026-09-22 (acceptance.md:233-244).
