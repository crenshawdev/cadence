# Phase 3: The store and its queries - Plan 2

## Goal

The binary owns the two-layer configuration and automatically imports a pre-4.0 planning directory into the new stores. Every mutation uses revalidated effective policy, and import leaves the original files available for rollback.

## Must be true when done

- AC5: First touch of a planning directory extracted from `v3.7.12` imports without hand edits, preserves every original file, and warns by name about all eight locked retirements.
- AC6: A config change between requests controls the next mutation; an unreadable config never permits mutation using a cached permission.
- Two paths naming one config file remain one layer with repo provenance; neither import nor reload silently manufactures two layers.
- Every frozen schema key has an explicit import disposition; retired settings are not effective settings.
- An interrupted import resumes without duplicate records, lost source material, or an apparent successful partial migration.
- Imported declines remain excluded from recall, including prose declines and earlier filed evidence of the same identity.

## Context

D-02, D-03, and D-06 bind this plan; D-01/D-05 persistence comes from completed PLAN-1.
The storage inventory and the 94-row config census are the grounding, not work to repeat; the seven flagged settings receive explicit rulings below.
Only the new Rust files and architecture note are leased. Legacy documents, user config, and `cadence-core/` are read-only inputs to planning and untouched originals during import.
All frozen source citations mean `git show v3.7.12:<path>`; phase derivation, dispatch resolution, and config menus remain outside this plan.

### Task 2: Revalidate both config sources before commit

## Notes

- Requirements use acceptance criterion IDs because phase 3 has no seeded requirement IDs. AC5 maps to Tasks 1, 4-6 and the combined test in Task 7; AC6 maps to Tasks 2-3 and 7. D-06 is specified in Task 1 and exercised on real frozen input in Task 6.
- Dependency: PLAN-1 must be complete. File leases do not overlap. PLAN-3 completes session-handler composition after this plan; the additional 2-before-3 wiring order is a planner choice to keep each intermediate tree compilable without shared module-root edits. No new CLI or MCP operation names are assigned here.
- Seven-key ruling: the six dispatch-token leaves are dead, not dormant effective limits. Frozen `cadence-core/bin/planning/trace.mjs:1282-1307` feeds them into a report and returns its comparisons; these are not pre-dispatch spend caps. The capture key retains its spelling and integer, with an explicit active-item reporting unit. Thus the original census remains 79 keep-resemantic / 8 dead / 7 UNSETTLED; this plan resolves it to 80 / 14 / 0, with no rename and no silent holding decision.
- Other planner choices: versioned config siblings preserve the originals; invalid/unknown material remains non-effective evidence; legacy global forge-repo values keep their provenance instead of the census's suggested drop; ambiguous cross-ledger identity is conservatively declined with a diagnostic; log order is source-relative when chronology cannot be established. Out-of-schema retired settings are additional named diagnostics, not additional rows in the 94-leaf census; do not auto-map an aggregate legacy policy into new role choices.
- D-03 is satisfiable as reversible access to legacy behavior: frozen readers open legacy names, for example `cadence-core/bin/planning/recall.mjs:104`, `:124`, `:178`. Checkout of old code can use the preserved files. A literal promise that `git checkout` alone removes newly created untracked stores or reverts uncommitted user-global output is not satisfiable; import must not claim that stronger guarantee.
- D-02's final revalidation has the same external check/replace race described in PLAN-1; no watcher or timestamp cache closes it. This plan neither adds locks nor treats stale permission as current.
- Verify commands are instructions for execution, not commands run during this planning task. Tests use temporary files and supplied global-config paths, never the planner's real user config, and never execute the frozen test suite or write `cadence-core/`.
