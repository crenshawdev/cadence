# Phase 38: The suite is a gate, not a guillotine

## Scope boundary

Two execution-model rules were decided under 3.7.12 before the binary had executed a plan, and every native plan since has paid for them. One: a red suite ends the plan. D-112 (.planning/phases/12/CONTEXT.md:207, 2026-09-10) says one suite launch per plan; acceptance.md rule 5 (docs/architecture/acceptance.md:390-398, 2026-09-09) says once at the close; execution/history.rs:651 refuses suite-once and :714 refuses completion, and D-120 makes the only repair a new gap plan. Sixteen native plans have run (phases 31, 34, 36, 37); seven went red at that line and every one became a planning cycle. In two of them (31-2, 37-2) the executor had the fix in hand and the rule forbade committing it. Two: a dispatch's identity is its prompt byte count under today's renderer. Phase 6 (.planning/phases/6/CONTEXT.md:266, 2026-07-29) recorded that the active dispatch carries a byte count with no renderer version and replay refuses a length mismatch; execution_service.rs:1795-1806 re-renders every outstanding dispatch and refuses prompt-mismatch, already through one historical-renderer shim. Checked-in skills must byte-equal the render (tests/mcp.rs:1266, tests/phase13_verification.rs:1209) and prompt digests are pinned in tests (tests/phase8_dispatch.rs:1125). So any change to shared instruction text breaks every pinned rendering in files no lease names and refuses every dispatch issued before it; eight of the nine failures at 863b49ea are this. This phase re-decides both rules with that evidence. A red suite raises a repair checkpoint the owner answers; one repair and one rerun are allowed on the record; a second red blocks as today; gap plans remain for redesigns. A dispatch retains the prompt it was issued with and answers with it; nothing re-renders. Files the binary renders are regenerated by the binary and are inside every lease by rule. execute-next takes a plan number. The suite receipt always carries the failing test names. Lease: crates/cadence/src/execution/{history,dispatch,model,runner,render,instructions}.rs, crates/cadence/src/execution_service.rs, crates/cadence/src/server.rs, docs/architecture/acceptance.md, the rendered skills/*/SKILL.md, and their tests. The plans of this phase are landed by hand with the executor block, red then green, signed, because the rules being replaced are the ones that would block their own native execution; verification runs natively. Phase 31's close is the first consumer and the first dogfood.

## Durable decisions

- D-163. Supersedes the once-per-plan clause of D-112 and acceptance.md rule 5. A suite launch that reports a failure ends the launch, not the plan. The binary raises a repair checkpoint carrying the failing test names and the files the executor names for the repair; the owner's answer authorizes exactly one repair and exactly one further suite launch on the same plan. Every launch, result, checkpoint, answer and repair commit is retained in the plan's history. A second failing launch blocks the plan exactly as a first one does today. The dead-launch relaunch of D-112 is unchanged and counted apart from the repair. If wrong: the executor loops without the owner, or a repair leaves no trace.
- D-164. Amends D-120. A gap plan repairs a plan the owner refused to repair at the checkpoint, a plan whose second launch failed, or a redesign; never a first red suite. A repair inside the plan that touches files outside the admitted lease is retained as a deviation on the plan record, named per file, and the verifier reads it. If wrong: a first red costs a planning cycle again, or an out-of-lease edit hides.
- D-165. Supersedes the phase 6 byte-count identity. An admitted dispatch retains the exact prompt it was issued with and its digest; the dispatch answer returns the retained prompt; nothing re-renders an outstanding dispatch under the current renderer, and the historical-renderer path is removed. A renderer change never refuses an earlier dispatch, so the binary can be rebuilt while a plan is dispatched. If wrong: an upgrade strands every open plan, or a prompt on the wire differs from the one admitted.
- D-166. Files the binary renders from compiled-in text (the skills the render table in tests/mcp.rs names, and prompt receipts) are regenerated by the binary and are inside every task lease by rule. A task whose change alters rendered text commits the regenerated files in the same commit; the guard refuses a hand edit to a rendered file. The planner never lists them. If wrong: a shared-text change breaks tests no lease can reach, or a skill file drifts from its source by hand.
- D-167. execute-next accepts an optional plan number from the owner. Without it the first admitted plan without an outcome dispatches, as today. With it, the named admitted plan without an outcome dispatches ahead of earlier ones, and the answer records that the owner chose the order. If wrong: a gap plan lands behind the plans it repairs and the only exit is retire and re-issue.
- D-168. A suite receipt always carries every line that names a test result, whatever the output size; the 65,536-byte retention bounds the rest of the output, not the result lines. If wrong: the executor is asked to repair failures it cannot see.

## Decisions

- D-169. Phase-local. This phase's plans are executed by hand under the executor block with red and green commits and a signed history, not through execute-next, because the rules they replace are the rules that block native execution; verification runs natively through verify-next. Recorded here so the exception has one home, as docs/rationale/bootstrap-exception.md records the earlier ones.

## Truths

- T1. When a plan's suite launch reports a failure, the owner sees one repair checkpoint naming the failing tests and the files the executor proposes to touch, and no blocked plan.
- T2. When the owner has approved a repair checkpoint, the owner sees a second suite launch accepted on the same plan with both launches and both results retained in execution-history.
- T3. When a plan's second suite launch reports a failure, the owner sees the plan blocked with a suite-failed blocker and a third launch refused.
- T4. When the binary's renderer has changed after a dispatch was admitted, the owner gets the admitted dispatch's retained prompt byte for byte from execute-next, never prompt-mismatch.
- T5. When a task's commit changes text the binary renders into a skill file, the owner sees the regenerated skill file accepted inside the task's lease with the suite green.
- T6. When the owner names an admitted plan number to execute-next, the owner gets that plan dispatched ahead of an earlier admitted plan that has no outcome.
- T7. When a suite's output exceeds 65,536 bytes, the owner sees every failing test's name in the retained suite receipt.

## Flagged assumptions

- Each of the seven red suites had one cause and one owner-approved repair would have closed six of them; this is inferred from the retained blockers and the hand repairs (7d60cd9c, 167f7e39), not observed, and phase 31's close under D-163 is the first observation.
- Retaining a rendered prompt per dispatch (about 36 KB each at plan 8) does not reproduce the resident memory growth that JSON int-array stdout caused; measured at this phase's close.
- Regeneration by the binary is the only writer of rendered skill files; if a rendered file needs prose the source does not carry, the source changes, never the file.
