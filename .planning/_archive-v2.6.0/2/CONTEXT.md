## Durable decisions

- D-01 (Drift verdict): `/cad-audit`'s version-drift signal is VERDICT-MOVING - a FAIL that blocks the ship - exempted when the version is already tagged AND the manifest already carries it. Chosen over an additive report because FRI-03's own wording is "mechanically, rather than only reported", and the prose rule already reports it. The exemption is what stops the check firing on a close interrupted between the tag (milestone.md step 2) and the PROJECT.md evolve (step 4). Evidence: `cadence-core/workflows/audit.md:103-135` (FAIL blocks a ship and is not to be softened; the additive keys are a separate class), `cadence-core/workflows/milestone.md:12-18`, `:30-38`, `:66-69`, `:87-89`.
- D-02 (Drift test shape): The mechanical test is "the planning-doc version is one the project has ALREADY PUBLISHED", never a literal `docs != manifest` comparison. At the only point `/cad-audit` runs inside a close the two legitimately disagree, and ahead-of-manifest is the normal mid-cycle state - this repo is in it right now (`.claude-plugin/plugin.json` at `2.5.0`, `.planning/PROJECT.md:103` naming `v2.6.0`). Evidence: `skills/cad-health/SKILL.md:72-87` (a manifest equal to Active is "expected mid-close" and a note, never drift).
- D-03 (Comparand is tags): The `/cad-audit` arm compares against the repo's git TAGS, not `pluginVersion()`. The only manifest reader in this tree resolves relative to the SCRIPT, so in any project that is not Cadence it would compare the user's milestone against Cadence's own version. Evidence: `cadence-core/bin/git-branch.mjs:34-49` (states this verbatim as its own D-03), `cadence-core/bin/planning.mjs:81-100` (`MANIFEST_PATH` is script-relative), `:1165` (that version is emitted as provenance only).
- D-04 (Membership preserved): The published-version guard's MEMBERSHIP semantics are not re-tightened. A version that merely sorts below the newest tag is not drift, and any new consumer passes `publishedVersions` - the retired scalar key yields no comparand at all. This is phase 1's assignment rows 15 and 16 routed here as inputs, recorded precisely so the loosening is not reversed by accident. Evidence: `.planning/phases/1/SUMMARY.md` rows 15-16, `cadence-core/bin/lib/branch-decision.mjs:99-110`, `:152-153`, `:183-190`.
- D-05 (One cap, one place): The re-arm cap is written once in the consequence gate every fire site shares - `references/triage-gate.md`'s blocking arm, reached from `review-triggers.md` step 6 - not per workflow. There are five fire sites (`execute.md`, `task.md`, `debug.md`, `verify.md`, `git-guard.md`); a per-workflow cap would bound one of four paths and leave `cad-debug`, `cad-task` and `cad-verify` unbounded. Evidence: `cadence-core/references/triage-gate.md:8-11` (the unbounded "resume only after they are fixed (re-run fire)"), `cadence-core/references/review-triggers.md:186-192`, `:202`, and the five sites; `cadence-core/workflows/execute.md:303-307` already names this unbounded re-arm as a thing not to replicate.
- D-06 (Cap shape follows the shipped one): The cap reuses the shape of the one bounded loop already in the spine - a stated maximum of ONE re-arm, a NARROWED second pass, and a terminal ask handing the remainder to the user with a named reason. Chosen so the spine's two blocking loops explain themselves in one vocabulary rather than two. Evidence: `cadence-core/workflows/plan.md:212-236` ("ONE revision, maximum", the narrowed re-check, "Never loop again"), `:309`.
- D-07 (Spike precedes the value): The `maxTurns` spike runs BEFORE any value ships, recorded as `.planning/spikes/<slug>/SPIKE.md` with its criteria written before the experiment; whether a value ships in this phase at all is the spike's verdict to decide. ## Decisions

- D-08 (Walk mechanism): The bar and the run-everything-else behaviour ship as prose inside `verify.md`'s existing `walk` step, not as a new seam subcommand. The mechanism already exists: the walk chains on the seam's `next` (first `pending` item), so an item the model executes and records simply stops being offered. Evidence: `cadence-core/workflows/verify.md:140-176`, `cadence-core/bin/planning.mjs:457-459` (`nextPending`), `:573-588`.
- D-09 (`why_human` needs a seam change): The verifier's `why_human` does NOT survive into UAT.md today. Carrying a per-item machine-readable marker requires three coordinated edits - the `human_checks` append, the `UAT_FIELDS` render whitelist, and the template's field vocabulary - and is not a prose-only change. Evidence: `cadence-core/bin/planning.mjs:717-742` (the append drops it), `cadence-core/bin/lib/planning-files.mjs:942-943`, `:1066` (unregistered fields are destroyed by the first `record` rewrite), `skills/cad-verifier-contract/SKILL.md:182-186`.
- D-10 (Record one at a time, not via merge): Model-executed results are recorded through `uat record ... --evidence`, never by writing a payload and reusing `uat merge`. `merge` atomically overwrites `phases/<N>/FINDINGS.json` on every success, so a walk that merged its own results would clobber the deep pass's envelope - the file that exists to make a discarded verifier finding recoverable. `uat record` already accepts `--evidence` and `--source`, so no CONTRACTS change is needed. Evidence: `cadence-core/bin/planning.mjs:744-777`, `cadence-core/bin/self-verify.mjs:138-141`, `cadence-core/workflows/verify-deep.md:52-59`.
- D-11 (Model provenance is its own value): A result the MODEL executed carries provenance distinct from both a user answer and `source: verifier`, so the report's "auto-verified" count and the template's definition of `source: verifier` stay true. `source` has exactly one special value today and no enum validation, so an unknown string is accepted and silently not stored - the value must be registered, not just written. Evidence: `cadence-core/bin/planning.mjs:546-549`, `:574`, `cadence-core/templates/UAT.md`, `cadence-core/workflows/verify.md:260`, `:275-276`.
- D-12 (`maxTurns` is per-file): `maxTurns` appears nowhere in `agents/`, `skills/`, `cadence-core/` or the seams today, and it is a per-FILE frontmatter field, not per-dispatch. "Every dispatched agent carries a bound" therefore means editing the 19 rung files, and the value cannot vary by dispatch the way `model` can. Writing it into the spawn-agent seam instead would reproduce the resolved-then-silently-dropped shape already documented for per-trigger `effort`. Evidence: repo-wide grep (only `.planning/spikes/xhigh-executor-truncation/SPIKE.md:53-77`), `cadence-core/references/seams.md:46-60`, `cadence-core/bin/self-verify.mjs:700-777` (frontmatter is read for `tools:`/`skills:`/`effort:` only; a new key is accepted).
- D-13 (One dispatch path is uncovered): `new-project.md`'s research step dispatches an unnamed generic agent Cadence owns no file for, so it is outside any frontmatter bound. The phase either excludes it explicitly with its reason or gives it a Cadence agent file - it may not be silently counted as bounded. Evidence: `cadence-core/workflows/new-project.md:147-149` against `cadence-core/route-table.json:17` and the 19 files in `agents/`.
- D-14 (Round count is prose state): The re-arm round count is orchestrator-context state expressed in prose, not persisted state. Nothing counts fires today, and the alternatives - a new trace event plus a reader arm, or a `review.max_rounds` config key with its schema, `config-reach.md` and catalog rows - do not fit beside FRI-01 and FRI-03 under an 8-task ceiling. The known cost is stated: a `/clear` between rounds resets the counter. Evidence: `cadence-core/bin/lib/trace.mjs:50` (four families, free-text `--event`; read with `grep -a`), `cadence-core/references/review-triggers.md:172-176`, `cadence-core/references/seams.md:57-60`, `cadence-core/bin/planning.mjs:830-931` (`audit` reads no trace).
- D-15 (Prose version reader is reused): The planning-doc version is read as `PROJECT.md ### Active` first with the `ROADMAP.md` `# ` title as fallback - the same precedence branch naming uses - by exporting `activeVersion`/`titleVersion` from `branch-decision.mjs` for drift detection only, keeping REL-03's ban on release derivation intact. A second prose reader beside the first is exactly the drift both modules' single-reader discipline was written to prevent. Note this repo's `ROADMAP.md:1` is `# Roadmap` with no version token, so the fallback arm yields null here. Evidence: `cadence-core/bin/lib/branch-decision.mjs:42-59`, `:61-71`, `:11-18`, `cadence-core/bin/git-branch.mjs:72-75`.
- D-16 (self-verify arm CUT): **Dropped 2026-08-08 by a scope cut; FRI-03 is narrowed to the `/cad-audit` arm alone.** `QW-04` already shipped a published-version guard AND a `/cad-health` prose rule, so building a self-verify arm as well meant detectors two and three for one incident that is already caught. `/cad-audit` is the arm that matters because it is the ship gate a close runs through, and one detector at the gate is the whole requirement. The original design is preserved for whoever revives it: the arm would compare `<root>/.claude-plugin/plugin.json` against `<root>/.planning/PROJECT.md`, gated so a `--root` fixture without `.planning/` stays lenient rather than failing, since the tracked planning docs mean CI has them. Evidence: `cadence-core/bin/self-verify.mjs:364-402` (`isFullTree`, D-03 fixture leniency), `:249-256`, `.github/workflows/test.yml`.
- D-17 (AC6 is proved against the repo's own script): The new seam output is unobservable through the `/cad-audit` slash command until the plugin is reinstalled, because the skill resolves its seam through `${CLAUDE_PLUGIN_ROOT}`. The fixture therefore exercises the repo's script and test file, using the hermetic `CADENCE_PLUGIN_MANIFEST` injection already in place, not the installed command. Evidence: `skills/cad-audit/SKILL.md:30`, `cadence-core/workflows/audit.md:19`, `:48`, `cadence-core/bin/planning.test.mjs:2538-2557`.
- D-18 (Budgets are regenerated in-phase): `cadence-core/bin/weight-budgets.json` is regenerated as part of this phase. Every prose surface it touches sits at EXACTLY its budget today - `verify.md` 13758/13758, `review-triggers.md` 15134/15134, `triage-gate.md` 3050/3050, `audit.md` 9894/9894, `skills/cad-health/SKILL.md` 5701/5701, `templates/UAT.md` 5276/5276, and each of the 19 `agents/*.md` - so any added sentence is a hard `budget-overrun` in CI. Evidence: measured 2026-08-08; `cadence-core/bin/self-verify.mjs:610-638`, `cadence-core/bin/weight-budgets.json:2`.
- D-19 (The 15,134 B figure moves with the file): Growing `references/review-triggers.md` past 15,134 B invalidates a figure two skills hardcode and `seams.md` makes mandatory for future deferrals. Either both lines are updated in the same phase or the new prose lands in `triage-gate.md` instead - which D-05 already prefers. Evidence: `skills/cad-land/SKILL.md:44`, `skills/cad-plan-review/SKILL.md:39`, `cadence-core/references/seams.md:240-243`, `cadence-core/bin/lib/deferred-reads.mjs:81-109`.
- D-20 (Contract rows ship with their surface): Any new `planning.mjs` flag or subcommand lands with its `CONTRACTS` row, and any new config key with its `config-reach.md` row, in the SAME task. Self-verify enforces both directions, so a missing row is a silent opt-out or a CI failure on the introducing commit - and an unplanned repair task does not fit an 8-task ceiling. ## Acceptance criteria

- [ ] AC1: `cadence-core/workflows/verify.md` states the human-check bar explicitly - an item is human-verify only when the model cannot execute it (irreversible against real data, or outside its reach: credentials, GUI, hardware, another machine)
- [ ] AC2: Running a walk over a checklist of 9 read-only-command items and 1 destructive item ends the turn asking about exactly 1 item; the other 9 are recorded with their evidence and shown as executed-and-cited rows, and a model-executed result is distinguishable in `UAT.md` from both a user answer and a deep-pass verifier result

- [ ] AC4: A spike file records what a `maxTurns`-capped run actually returns (partial work or failed dispatch) with a validated / invalidated / inconclusive verdict, written before any value ships
- [ ] AC5: Every dispatched agent carries an explicit runaway-loop bound, or a dispatch path that does not is named in the phase record with its reason
- [ ] AC6: `/cad-audit` FAILs on a planning-doc version the project has already published, proved by a fixture; it does not fail when the version is tagged and the manifest already carries it, and an untagged version that merely sorts below the newest tag is not drift
- [ ] AC7: `node --test cadence-core/bin/*.test.mjs` and `self-verify` both pass with `weight-budgets.json` regenerated (the self-verify DRIFT arm this criterion also required was cut 2026-08-08 with D-16; what remains is that the phase's edits leave both gates green)
